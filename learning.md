# WorkspaceScripts — Learnings

Not a Salesforce project itself. It's a personal Bash toolkit that manages **git worktrees**
for Salesforce projects (and generic git repos), so you can work on multiple
branches/tickets side by side without re-cloning or stashing.

## Entry point

- `./ws` → execs `scripts/ws-ui.sh`, a `dialog`(1)-based TUI menu with actions:
  `setup`, `worktree` (create), `select`, `remove`, `exit`.
- `scripts/install.sh` — symlinks `./ws` into `~/.local/bin/ws` (or a custom
  `--bin-dir`/`--name`) so the toolkit can be run as a plain `ws` command from any
  directory, without `cd`ing into the repo. It's a symlink (not a copy), so toolkit
  updates apply immediately. Idempotent (safe to re-run), refuses to clobber an unrelated
  existing file unless `--force`, warns if the target bin dir isn't on `PATH`, and supports
  `--uninstall` to remove it again.
- `ws-ui.sh` runs each sub-script with `WS_FROM_WS_UI=1 WS_UI_MODE=dialog`. Sub-scripts
  behave differently depending on `WS_UI_MODE` (dialog boxes vs plain stdout/stdin prompts)
  and on whether they were sourced vs executed vs run from the TUI.
- Special exit code **10** from `select-project.sh` / `create-worktree.sh` means: "user
  chose to jump into the project" — the path is written to `config/.ws-ui-cd-next`,
  `ws-ui.sh` reads it, `cd`s there, and `exec`s a new interactive `bash --init-file ~/.profile -i`.

## Config

- `config/env.local.sh` (gitignored, generated by `scripts/setup.sh`) defines:
  - `WS_GIT_REPO_ROOT` — path to the main git repo/clone.
  - `WS_GIT_WORKTREE_PATH` — directory where new worktrees are created.
  - optional `WS_SF_PROJECTS_ROOT` — if Salesforce package folders aren't direct children
    of the repo root.
  - optional `WS_SF_MODE` — explicit `1/0` (or `true/false`, `yes/no`, `on/off`) override for
    whether the repo is treated as a Salesforce repo; overrides the basename heuristic.
  - optional `WS_SF_PACKAGES` — space-separated list of Salesforce package names for the
    package picker; defaults to `Recruitment BusinessCentral Workforce Maia`.
  - optional `WS_OPEN_TERMINAL_HOOK`, `WS_WT_WINDOW_ID` — for `lib/ws-open-terminal.sh`.
- `config/env.local.sh.example` is the template; `scripts/setup.sh` writes the real file
  interactively (works in both dialog and plain-terminal modes) and `chmod 600`s it.
- `scripts/ws-ui.sh` hands each project-jump path to its child script via a per-invocation
  `WS_UI_CD_NEXT_FILE` (`mktemp`'d under `config/`, e.g. `.ws-ui-cd-next.XXXXXX`) instead of
  a single fixed filename, so concurrent `ws` sessions don't race on the same handoff file.

## Core scripts (`scripts/`)

- `setup.sh` — prompts for repo root & worktree path, validates them, writes `env.local.sh`,
  then automatically runs `scripts/install.sh` (default `~/.local/bin/ws`) so the `ws`
  command is ready to use right after setup — no separate install step needed. Install
  failure is reported but non-fatal (setup still succeeds; you can retry with
  `scripts/install.sh`).
- `create-worktree.sh` — prompts for project type (`BUG`/`ITEM`/`OTHER`), a numeric ID, and
  a free-text name; sanitizes the name into `Title_Case_With_Underscores`; builds branch
  name `PREFIX+NUM_Name` (e.g. `BUG1234_Work_Item_Test`) and runs
  `git worktree add -b "$branch" "$dest"`. Shows a live `dialog --gauge` progress bar while
  git runs in the background. If the configured repo is a "Salesforce repo" (basename
  contains `Salesforce`), it also asks which package (Recruitment/BusinessCentral/
  Workforce/Maia) and records it in a `.ws-sf-package` marker file next to the worktree, and
  places the worktree at `.../<slug>/Salesforce` instead of `.../<slug>`.
- `select-project.sh` — lists existing worktrees under `WS_GIT_WORKTREE_PATH` (parsed from
  `git worktree list --porcelain`), lets you pick one, and cds into it (or into the saved
  Salesforce package subfolder, via the `.ws-sf-package` marker).
- `remove-project-worktree.sh` — picks a worktree (excludes the main repo), confirms, then
  runs `git worktree remove` (falls back to `--force`) and optionally `git branch -d`/`-D`.
  Afterwards it also deletes the leftover top-level project folder (e.g. `./ITEM1234`) via
  `rm -rf`, since `git worktree remove` only removes the worktree's own directory — for
  Salesforce repos the worktree lives one level down (`ITEM1234/Salesforce`), so the parent
  `ITEM1234` folder (and its `.ws-sf-package` marker) would otherwise be left behind. This
  cleanup only runs if Git no longer lists the worktree (removal actually succeeded) and only
  ever targets a path under `WS_GIT_WORKTREE_PATH` (never `WS_GIT_WORKTREE_PATH` itself).
- `sf-*.sh` (`sf-recruitment.sh`, `sf-businesscentral.sh`, `sf-workforce.sh`, `sf-maia.sh`) —
  tiny wrapper scripts that source `lib/sf-goto-package.sh` and jump straight into one
  Salesforce package folder, without going through the worktree list UI.

## Library (`scripts/lib/`)

- `worktree-list.sh` — shared parser for `git worktree list --porcelain`.
  `wt_list_raw <repo_root> <wt_base> [exclude_repo_root=0|1]` prints `path<TAB>branch`
  lines (realpath-resolved, filtered to `wt_base`, optionally excluding the main repo root).
  Used by both `select-project.sh` and `remove-project-worktree.sh` (previously duplicated
  inline in each script).
- `sf-package.sh` — shared Salesforce package helpers: `sf_package_list` (reads
  `WS_SF_PACKAGES`, space-separated, falling back to the built-in default
  `Recruitment BusinessCentral Workforce Maia`), `prompt_sf_package` (menu built from
  `sf_package_list`), `is_salesforce_repo` (explicit `WS_SF_MODE=1/0/true/false/yes/no`
  override, else falls back to the basename-contains-"Salesforce" heuristic),
  `sf_resolve_package_dir`, `sf_package_marker_path`, `read_saved_sf_package`.
- `sf-goto-package.sh` — `_sf_goto_package <pkg>` used by the `sf-*.sh` wrappers.
- `ws-open-terminal.sh` — `ws_open_terminal_in_dir`, best-effort helper to open a new
  terminal tab/window (tmux, Windows Terminal, gnome-terminal, konsole, alacritty, xterm)
  in a given directory; supports a custom `WS_OPEN_TERMINAL_HOOK` override. Not used by
  the dialog TUI flow currently (which just shows/cds to a path).

## Conventions worth remembering

- All scripts use `set -euo pipefail` (or `-uo pipefail` for the top-level UI, which must
  not die on submenu error codes).
- Scripts detect interactivity via `[[ -t 0 && -t 1 ]]` and behave as: sourced (just `cd`),
  executed on a TTY (`cd` + exec a nested interactive shell), or non-interactive (print the
  `cd` command for the user to run manually).
- `WS_UI_MODE=dialog` toggles between `dialog` widgets and plain `echo`/`read` prompts
  throughout — most user-facing scripts implement both code paths.
- Branch/worktree naming: `<TYPE><NUM>_<Sanitized_Name>` e.g. `ITEM42_Fix_Login_Bug`;
  sanitization replaces non-alphanumerics with `_`, collapses repeats, trims, then
  Title_Cases each `_`-separated segment.
- Nothing here touches Salesforce metadata/CLI directly — it only manages filesystem
  layout (git worktrees + package subfolder navigation) for Salesforce monorepos.
